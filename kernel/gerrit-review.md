# Gerrit review output (gerrit-review.json)

Lustre reviews are posted to Gerrit, not emailed to a mailing list. Instead of
the plain-text `review-inline.txt`, produce a single JSON file,
`./gerrit-review.json`, in the current directory (never the prompt directory).
The file is a Gerrit `ReviewInput` body that can be POSTed to:

    POST /changes/{change-id}/revisions/{revision-id}/review

(the harness that runs the review fills in change-id/revision-id; you only
produce the JSON body).

Create `./gerrit-review.json` only when regressions/issues are found. The
content/phrasing rules below replace the mailing-list framing of
inline-template.md, but the *thinking* about what counts as an issue is
unchanged.

## ReviewInput structure

```json
{
  "tag": "autogenerated:ai-review",
  "message": "<short overall summary; 1-3 sentences of plain text>",
  "comments": {
    "<file path>": [
      {
        "line": <int, line in the patched (new) file>,
        "message": "<the review comment>",
        "unresolved": true
      }
    ]
  }
}
```

Field rules:
- `comments` is a map: key = file path **relative to the repo root, exactly as
  Gerrit stores it** (e.g. `lustre/osc/osc_request.c`), value = array of comment
  objects on that file.
- Each comment object:
  - `line`: 1-based line number in the **new** (post-patch) file — this is the
    `REVISION` side, which is the default. Use the line you actually read from
    the checked-out worktree (the worktree has the commit applied, so its line
    numbers match the revision Gerrit will display).
  - `range` (optional, preferred when the issue spans a region): object with
    `start_line`, `start_character`, `end_line`, `end_character` (0-based
    characters, 1-based lines, end exclusive of character). When you give a
    `range`, also set `line` to `range.end_line`.
  - `message`: the comment text (see phrasing rules below).
  - `unresolved`: `true` for anything you want a human to act on (all real
    findings). Use `false` only for pure informational notes.
  - `side`: omit for the new file. Use `"PARENT"` only to comment on a line that
    exists solely in the pre-patch file (rare).
  - `in_reply_to`: omit (we are not threading onto existing comments).
- `message` (top level): a brief, neutral summary. Do not restate every finding;
  one or two sentences (e.g. "Two possible regressions and one commit-message
  question, noted inline."). Plain text.
- `tag`: keep `"autogenerated:ai-review"` so the comments are clearly marked as
  machine-generated.
- **Labels / voting:** do NOT include a `labels` field by default. Leave the
  Code-Review vote to a human. (A wrapping pipeline may add a label; the review
  itself should not vote.)
- Do not invent other top-level fields.

### Commit message comments

To comment on the commit message, use the magic path `"/COMMIT_MSG"`.

Gerrit's `/COMMIT_MSG` pseudo-file has a 6-line generated header (`Parent:`,
`Author:`, `AuthorDate:`, `Commit:`, `CommitDate:`, blank), so the real commit
**subject is line 7**, and body lines follow. Account for this +6 offset when
anchoring to a specific commit-message line. If you are unsure of the exact
line, omit `line` to attach a file-level comment to the commit message instead.

### Patchset-level (overall) comments

For an observation about the whole change that has no single file/line (e.g.
"this should be split into two patches", "missing test coverage", "Fixes: tag
needed"), use the magic path `"/PATCHSET_LEVEL"` with no `line`.

## Phrasing rules (carried over from inline-template.md)

These still apply — Gerrit comments are read by the same maintainers:

- Comments are plain prose anchored to a line. Because the comment is already
  attached to the code, **do not quote the diff or use `> ` email quoting**, and
  **do not restate the line number in the text** — the anchor does that.
- Be factual and undramatic. Frame findings as questions, not accusations, and
  do not address the author personally.
  - not: "You leak the folio here." -> "Can this leak the folio if
    cl_page_find() fails?"
- Name the specific thing. Not "resource leak" but "does this leak `lock`?";
  not "possible overflow" but "can `idx` exceed `lsm_entry_count`?".
- Vary your phrasing; don't open every comment with "Does this code ...".
- Keep comments short. Use small plain-text code snippets or `funcA()->funcB()`
  call chains instead of dense paragraphs. Break a multi-sentence comment into
  short logical groups.
- No ALL-CAPS labels (no `REGRESSION:`, no `SYZKALLER-1:`). State the issue
  plainly. Gerrit renders limited markdown; a short ```code``` fence or a blank
  line between paragraphs is fine, but keep it minimal.
- For subjective/style findings (SR-* patterns, or Adilger-style nits from
  lustre-style.md), soften: "this isn't a bug, but ..." / "if the patch is
  refreshed, consider ...".
- Don't over-explain obvious copy/paste or forgotten-update mistakes; a one-line
  note is enough. Don't explain why a typo is bad — just point it out.
- Include every confirmed issue; never include findings you decided were false
  positives.

## Severity markers

Lustre reviewers prefix each comment with a severity/category marker. Use the
same convention so the comments read as familiar; start the comment `message`
with the marker. The topic guides (lustre-style.md, wire-protocol.md, tests.md,
lustre-utils.md, lustre-commit-message.md) tell you which marker fits each rule.

- **`(defect)`** — a real correctness / ABI / protocol / memory bug. Report as a
  regression; these justify a negative review.
- **`(style)`** — coding-style / formatting / convention. Cosmetic but expected
  to be fixed; phrase as "this isn't a bug, but ...".
- **`(minor)`** — small optional improvement, often "if the patch is refreshed".
- **`(typo)`** — spelling/wording in code, comment, or commit message.
- **`(suggestion)`** — optional design/optimization idea.

Don't flood a patch with dozens of nits; prioritize `(defect)` and the
highest-value `(style)` items, and anchor each to its own line.

## Worked example

```json
{
  "tag": "autogenerated:ai-review",
  "message": "One possible reference leak and a commit-message question, noted inline.",
  "comments": {
    "/COMMIT_MSG": [
      {
        "line": 7,
        "message": "The subject says \"osc:\" but the diff is entirely under lustre/mdc/. Should the component tag be mdc?",
        "unresolved": true
      }
    ],
    "lustre/osc/osc_request.c": [
      {
        "line": 1423,
        "message": "If osc_extent_find() returns an error here, is `oap` still freed on the way out, or does this path leak it?\n\n    rc = osc_extent_find(...);\n    if (rc)\n        return rc;   /* oap allocated above */",
        "unresolved": true
      }
    ],
    "/PATCHSET_LEVEL": [
      {
        "message": "This adds a new on-wire flag in lustre_idl.h; wirecheck.c and both wiretest.c copies don't seem to be updated to match. Should they be?",
        "unresolved": true
      }
    ]
  }
}
```

## Validity check (mandatory)

After writing `./gerrit-review.json`:
- Confirm it is valid JSON (no trailing commas, all strings escaped). If you can
  run a tool, `python3 -m json.tool ./gerrit-review.json` must succeed.
- Confirm every key under `comments` is a real file path from this patch (or one
  of the magic paths `/COMMIT_MSG`, `/PATCHSET_LEVEL`).
- Confirm no finding you classified as a false positive made it in.
- Regenerate the file if it is malformed.
